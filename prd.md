## 8. Easy Updates: Selected Approach A

**Use reusable HTML templates.**

Laleen edits her website directly through GitHub and is still learning how to code.

She must be able to add new projects or labs without changing the website's styling or JavaScript.

Create consistent, clearly commented HTML entries for:

- Completed projects.
- Hack The Box labs.
- CTFs.
- Technical write-ups.
- Other relevant technical work.

Each entry should have optional fields for:

- Title.
- Category.
- Status.
- Short description.
- Technologies and tools.
- Personal contributions.
- What was learned or accomplished.
- Screenshot or image.
- Repository or write-up link.

All information must remain accessible without JavaScript.

Use existing CSS classes and reusable layouts.

New entries should inherit the day/night themes and responsive styling automatically.

Respect platform rules regarding Hack The Box walkthroughs, active machines, flags, and spoilers.

### Update guide

Create a beginner-friendly `UPDATING.md` explaining how to:

1. Find an existing HTML entry.
2. Copy it.
3. Replace the information.
4. Add an optional image.
5. Check links.
6. Run or verify safety checks.
7. Publish safely through GitHub.
8. Confirm the live website updated correctly.

### Important exclusions

- No Recent Activity section.
- No activity feed.
- No separate updates timeline.
- No JSON-generated project system.
- No static-site generator unless separately approved.

New work belongs in the appropriate existing section.

Build for maintainability now so future additions do not require a redesign.

## 13. Security and Privacy Rules

Preserve the existing project requirements.

- Static GitHub Pages hosting.
- No backend or database.
- No visitor accounts.
- No logins.
- No secrets, passwords, API keys, or tokens.
- HTTPS.
- Content Security Policy.
- No inline scripts or styles.
- No `eval`.
- Never insert visitor input as HTML.
- Fonts and libraries hosted locally.
- No third-party CDNs without approval.
- External links use `rel="noopener noreferrer"`.
- No analytics, trackers, or tracking cookies.
- No contact form.
- No phone number, home address, or GPA.
- No fake password gates.
- Label games and simulations accurately.
- No fabricated project results.

Resume location:

`assets/laleen-salim-resume.pdf`

Document GitHub Pages' security-header limitations honestly.

Keep the page accessible, responsive, and usable without JavaScript.

Run `node tools/check.mjs` before committing.

Inspect the existing GitHub workflow and recommend an appropriate way to check changes before publishing them.

Do not change publishing settings or introduce GitHub Actions without approval.

## 16. One-Hour Session Rules

Every session starts by identifying:

- Current phase and session.
- One specific goal.
- Expected files involved.
- What success looks like.

Do not begin multiple unrelated tasks.

When the hour is nearly finished, finish or safely pause the current change.

Never rush an incomplete change onto the live website.

Unfinished work should remain unmerged until it has passed review and tests.

### Session checkpoint

At the end of every session, Claude must provide:

**Completed:** What was finished.

**Files changed:** Which files were updated.

**Tested:** What tests passed or failed.

**Website status:** Whether the live site is unchanged or updated and verified.

**Next task:** One recommended task.

**Next prompt:** A short message Laleen can paste when returning.

The session checkpoint must distinguish verified results from work that still needs checking.
